# Data Dictionary

Column-level reference for every table. Relationships are drawn in the [ERD](erd.md).

## Conventions

| Convention | Rule |
|---|---|
| Schemas | One per module: `customer`, `product`, `policy`, `premium`, `claims`, `document`, `intelligence`, `audit`, `messaging` |
| Naming | `snake_case`, singular table names |
| Primary keys | `id uuid` (UUIDv7, generated by the application) unless noted |
| Business identifiers | Human-readable, unique, generated from a sequence: `CUS-000001`, `POL-2026-000001`, `CLM-2026-000001` |
| Money | `decimal(19,4)`; currency is `varchar(3)` ISO 4217 (with a `CHECK` on `^[A-Z]{3}$`; `char(n)` fails Hibernate schema validation) on the owning aggregate. Amounts are never negative — direction is expressed by type or direction columns |
| Timestamps | `timestamptz`, stored in UTC. Business dates (incident date, effective date) are `date` |
| Enums | `varchar` with a `CHECK` constraint, not PostgreSQL enum types, so new values are an additive migration |
| Audit columns | Mutable aggregate roots have `version bigint` (optimistic lock), `created_at`, `updated_at`, `created_by uuid`, `updated_by uuid`. These are listed once here and omitted from the tables below. In code they come from the `AuditedEntity` base class, which stamps them on insert and update (`created_by`/`updated_by` is the signed-in user, or the nil UUID for system work such as payment events); nobody sets them by hand |
| Users | User references (`*_by`, `assigned_to`) are Alensi Identity user IDs (the Keycloak `sub`). No foreign key — users live in Identity |
| Tenant | Every table holding insurer data has `tenant_code varchar(16) not null`, stamped from the current tenant when the row is first persisted (base class `TenantOwned`), never changed afterwards, and refused if the row is written while acting in another tenant (an Alensi Identity tenant, e.g. `JUB`). It leads every index, foreign keys between tenant tables are composite (`tenant_code`, `id`), every query filters on it, and a row-level security policy enforces it again in the database ([Row-Level Security](../api/authorization.md#row-level-security)). The `messaging` schema is the only exception. Like audit columns, it is omitted from the tables below |
| Unit scope | `unit_code` is the Alensi Identity target code of the owning team or branch. Authorization filters on it; see [Authorization](../api/authorization.md#record-ownership) |
| Soft delete | Not used. Records move to terminal statuses; personal-data erasure is handled by an anonymisation job |

Columns marked **PII** contain personal data and are excluded from AI prompts and non-essential logs (see [Intelligence Architecture](../ai/intelligence-architecture.md#data-protection)).

## Status Values

### Policy Status

| Status | Meaning |
|---|---|
| `QUOTED` | Priced and offered; valid until `quote_expires_at` |
| `REFERRED` | Eligibility rule or risk requires underwriter review in Flow |
| `DECLINED` | Failed a hard eligibility rule or declined by an underwriter |
| `QUOTE_EXPIRED` | Quote not accepted in time |
| `PENDING_PAYMENT` | Accepted; waiting for the first installment |
| `ACTIVE` | In force |
| `LAPSED` | Installment unpaid beyond the grace period; can be reinstated by paying arrears within 30 days |
| `CANCELLED` | Terminated before expiry |
| `EXPIRED` | Reached expiry date |

### Installment Status

`SCHEDULED` → `DUE` → `PAYMENT_PENDING` → `PAID`, with `OVERDUE` after the due date, `WAIVED` by adjustment, and `CANCELLED` when the policy is cancelled.

### Payment Reference Status

| Status | Meaning |
|---|---|
| `INITIATED` | Row created, request to Pay not yet confirmed |
| `PENDING` | Pay accepted the request; awaiting provider outcome |
| `SUCCEEDED` | Money moved |
| `FAILED` | Pay reported failure |
| `CANCELLED` | Cancelled before completion |
| `REFUNDED` | A succeeded collection was refunded |
| `UNKNOWN` | The request to Pay timed out; resolved by re-sending with the same idempotency key or by a later Pay event |

### Claim Status

See [Claim Lifecycle](../flows/claim-lifecycle.md). Values: `SUBMITTED`, `INFORMATION_REQUESTED`, `UNDER_ASSESSMENT`, `AWAITING_DECISION`, `APPROVED`, `PARTIALLY_APPROVED`, `REJECTED`, `SETTLEMENT_IN_PROGRESS`, `SETTLED`, `CLOSED`, `WITHDRAWN`.

### Settlement Status

`PENDING` → `PAYMENT_INITIATED` → `PAID`, or `FAILED` (retryable with a new payment attempt) and `CANCELLED`.

### Anomaly Types

| Type | Detector logic (deterministic) |
|---|---|
| `DUPLICATE_CLAIM` | Same policy or customer, incident dates within 7 days, same incident type, amount within 10%, or identical document hash |
| `HIGH_CLAIM_FREQUENCY` | Claims per customer in the last 12 months above the product's 95th percentile |
| `AMOUNT_OUTLIER` | Claimed amount z-score > 3 against the coverage's settled-claim history, or above 90% of the limit |
| `EARLY_CLAIM` | Incident within 30 days of policy inception or reinstatement |
| `LATE_REPORTING` | Reported more than the product's notification window after the incident |
| `DATA_INCONSISTENCY` | Verified document extraction disagrees with claim data (date, amount, registration, patient name) |
| `LINKED_ENTITIES` | Phone, email, payee token, or address shared with other customers who have claims |
